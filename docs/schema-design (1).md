# Project Brain API: Schema Design

**Author:** Reshma Biju
**Started:** 4 November 2026 · **Last updated:** 4 November 2026
**Status:** Design complete (Steps 1 to 9). 

Overview

The database stores four things: users, their projects, the items inside each project (ideas, bugs, research, refactors, and features), and notes for each project.

* SQL Server runs locally in Docker for development, and on MonsterASP.NET in production.
* The schema will be created and changed with EF Core migrations (code-first). This document is the design those migrations follow.
* The ERD image is `schema-erd.png`. Keep it in the same folder as this file.

## Decisions at a glance

|Topic|Decision|Reason|
|-|-|-|
|Delete behaviour|Hard delete everywhere, with cascade. No soft delete.|There is no recovery, audit, or delete-account feature, so a delete flag would add complexity with no use.|
|Primary keys|GUIDs, generated by EF Core's SQL Server sequential generator. `DEFAULT NEWSEQUENTIALID()` stays in the hand-written script for direct SQL inserts.|Not random, so it avoids index fragmentation on a clustered key.|
|Category, Type, Status|`CHECK` constraints, not lookup tables.|Small, fixed lists. A lookup table would add tables and joins for no benefit now.|
|Ownership|Items and notes have no `UserId`. Ownership is checked through the project.|Each fact is stored once. See Step 4.|
|Text columns|`NVARCHAR`|Unicode, so names in any language are stored correctly.|
|Times|`DATETIME2(3)`, stored in UTC|Millisecond precision keeps ordering stable. UTC avoids time zone and daylight saving problems.|
|Import of old localStorage data|Out of scope. The API always generates ids.|Not needed for the first version.|
|Refresh tokens|Not needed now.|The API uses a JWT, and a token table can be added later.|

## 1\. Requirements

### Screens and what each one needs from the database

**Landing page.** Static. No database access. It only links to Login and Sign up.

**Login.**

* Look up a user by email. Needs the user's Id, Name, and password hash.
* The lookup needs an index on `Email`.

**Sign up.**

* Create an account. The email must not already exist: one email, one account.
* The duplicate check in the application gives a friendly message, but two people signing up at the same moment could both pass it. The real guarantee is a **unique index on `Email`**. The API catches the duplicate-key error and returns "email already exists" (HTTP 409).
* A logged-in user is redirected to the dashboard, so this case is a new visitor using an email that is already registered.

**Dashboard.**

* **Empty state:** shown when the user has no projects. It uses the project count from the stats query.
* **Focus projects:** the user's top 3 projects, pinned first, then most recently updated. Each card shows a progress percentage and an item count, so it also needs aggregates from the Items table.
* **Continue working:** the user's items with status `in-progress`, most recently **updated** first, limited to 5, with the project name.
* **Recent captures:** the user's newest items, ordered by **creation** date, limited to 5, with the project name.
* **Stats:** number of projects, and number of items in each status (captured, backlog, in progress, and done).
* **Quick Capture:** needs the list of the user's projects for the dropdown, and writes a new item.

**Projects.**

* List all of the user's projects, each with progress and item count.
* Search by project name, and filter by category.
* Actions: create, edit, pin or unpin, delete.

**Project detail.**

* One project with its summary: progress, and counts per status.
* **Items tab:** search by title or details, filter by status and type, add, edit, change status, delete.
* **Notes tab:** search by title or body, add, edit, delete.

**Settings.**

* Show the logged-in user's name and edit it.

### Business rules the database must support

* **Progress** = done items divided by committed items (backlog, in progress, and done), rounded to a whole number. Captured items are not counted. Zero committed items means 0%.
* **Last updated.** Any change to an item or a note also updates the project's `UpdatedAt`. Pinning or unpinning does **not**. This matches the React app. Item and note changes are two statements, so they run in **one transaction**.
* **Ownership.** Items and notes have no `UserId`. Ownership is checked through the project (`Projects.UserId = @userId`) **inside the same statement** as the read or write. If the data is not the user's, the API returns 404 so it does not reveal that the id exists.
* **Emails** are stored in lowercase and trimmed.
* **Times** are stored in UTC.
* **Derived values are never stored.** Progress, counts, and the focus order are calculated from the rows.

### SQL sketches for the key queries

These are drafts that show the shape of each query. They become repository methods in the API.

**R1: login lookup**

```sql
SELECT Id, Name, Email, PasswordHash
FROM dbo.Users
WHERE Email = @email;
```

**R4: focus projects with progress inputs**

```sql
SELECT TOP (3)
    p.Id, p.Name, p.Description, p.Category, p.IsPinned, p.UpdatedAt,
    COUNT(i.Id) AS ItemCount,
    SUM(CASE WHEN i.Status <> 'captured' THEN 1 ELSE 0 END) AS CommittedCount,
    SUM(CASE WHEN i.Status = 'done' THEN 1 ELSE 0 END) AS DoneCount
FROM dbo.Projects p
LEFT JOIN dbo.Items i ON i.ProjectId = p.Id
WHERE p.UserId = @userId
GROUP BY p.Id, p.Name, p.Description, p.Category, p.IsPinned, p.UpdatedAt
ORDER BY p.IsPinned DESC, p.UpdatedAt DESC;
```

**R5: continue working**

```sql
SELECT TOP (5)
    i.Id, i.Title, i.Type, i.Status, i.UpdatedAt,
    p.Id AS ProjectId, p.Name AS ProjectName
FROM dbo.Items i
JOIN dbo.Projects p ON p.Id = i.ProjectId
WHERE p.UserId = @userId AND i.Status = 'in-progress'
ORDER BY i.UpdatedAt DESC;
```

R6 is the same query without the status filter, ordered by `i.CreatedAt DESC`.

**R7: dashboard stats**

```sql
SELECT
    (SELECT COUNT(\*) FROM dbo.Projects WHERE UserId = @userId) AS ProjectCount,
    COUNT(CASE WHEN i.Status = 'captured'    THEN 1 END) AS Captured,
    COUNT(CASE WHEN i.Status = 'backlog'     THEN 1 END) AS Backlog,
    COUNT(CASE WHEN i.Status = 'in-progress' THEN 1 END) AS InProgress,
    COUNT(CASE WHEN i.Status = 'done'        THEN 1 END) AS Done
FROM dbo.Items i
JOIN dbo.Projects p ON p.Id = i.ProjectId
WHERE p.UserId = @userId;
```

**R10: a project's items with optional search and filters**

```sql
SELECT i.Id, i.Title, i.Type, i.Status, i.Details, i.CreatedAt, i.UpdatedAt
FROM dbo.Items i
JOIN dbo.Projects p ON p.Id = i.ProjectId
WHERE i.ProjectId = @projectId
  AND p.UserId = @userId
  AND (@search IS NULL OR i.Title LIKE '%' + @search + '%'
                       OR i.Details LIKE '%' + @search + '%')
  AND (@status IS NULL OR i.Status = @status)
  AND (@type IS NULL OR i.Type = @type)
ORDER BY i.CreatedAt DESC;
```

Notes on this query:

* The search text must be passed as a **parameter**, never joined into the SQL string. The characters `%` and `\_` in the user's text should be escaped so they are matched literally.
* The "optional parameter" pattern (`@x IS NULL OR ...`) can lead to poor query plans. In EF Core, the filters are added only when a value is present, which gives a simpler query each time.

**W7: add an item (shape of the transaction)**

```sql
BEGIN TRANSACTION;

INSERT INTO dbo.Items (Id, ProjectId, Title, Type, Status, Details)
SELECT @id, p.Id, @title, @type, @status, @details
FROM dbo.Projects p
WHERE p.Id = @projectId AND p.UserId = @userId;      -- ownership inside the statement

IF @@ROWCOUNT = 1
    UPDATE dbo.Projects SET UpdatedAt = SYSUTCDATETIME() WHERE Id = @projectId;

COMMIT TRANSACTION;
```

If the insert affects no rows, the project is not the user's (or does not exist), and the API returns 404. The final version needs error handling (`TRY...CATCH` with a rollback), or it is done through EF Core with one `SaveChanges` call.

## 2\. Entities

The app stores four things. Each one becomes a table.

|Entity|What it stores|Why it is a separate table|
|-|-|-|
|Users|an account: name, email, password hash|one row per person, referenced by many projects|
|Projects|a personal project, owned by one user|one user has many projects|
|Items|an idea, bug, research item, refactor, or feature, inside one project|a project has many items, each with its own status and type|
|Notes|a written note inside one project|a project has many notes|

**Considered and not added**

|Candidate|Decision|Reason|
|-|-|-|
|Sessions or refresh tokens|not added|the API uses a JWT, and a token table can be added later|
|Lookup tables for Category, Type, Status|not added|`CHECK` constraints are enough (see Step 6)|
|Tags, attachments, comments|not added|not in the app's first version|

## 3\. Attributes

### Users

|Column|Type|Required|Default|Notes|
|-|-|-|-|-|
|Id|uniqueidentifier|yes|`NEWSEQUENTIALID()`|primary key, generated by EF Core in the application|
|Name|nvarchar(60)|yes|none|display name|
|Email|nvarchar(256)|yes|none|login identifier, lowercase and trimmed, unique. 256 is the practical maximum length of an email address|
|PasswordHash|nvarchar(256)|yes|none|the hash only, never the password|
|CreatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC|

No `UpdatedAt` (nothing reads it) and no delete flag (no soft delete).

### Projects

|Column|Type|Required|Default|Notes|
|-|-|-|-|-|
|Id|uniqueidentifier|yes|`NEWSEQUENTIALID()`|primary key|
|UserId|uniqueidentifier|yes|none|foreign key to Users|
|Name|nvarchar(60)|yes|none|matches the form limit|
|Description|nvarchar(200)|yes|`''`|an empty string means "no description", matching the React code, so there is one form of "empty" and not two|
|Category|nvarchar(30)|yes|none|one of six values (`CHECK`)|
|IsPinned|bit|yes|`0`|drives the Focus projects order|
|CreatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC|
|UpdatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC. Changed by edits to the project, its items, and its notes, but not by pinning|

### Items

|Column|Type|Required|Default|Notes|
|-|-|-|-|-|
|Id|uniqueidentifier|yes|`NEWSEQUENTIALID()`|primary key|
|ProjectId|uniqueidentifier|yes|none|foreign key to Projects|
|Title|nvarchar(100)|yes|none|matches the form limit|
|Type|nvarchar(20)|yes|none|idea, bug, research, refactor, or feature (`CHECK`)|
|Status|nvarchar(20)|yes|`'captured'`|captured, backlog, in-progress, or done (`CHECK`). New items start as captured, as in Quick Capture|
|Details|nvarchar(1000)|yes|`''`|optional text, stored as an empty string when blank|
|CreatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC. Used for "Recent captures"|
|UpdatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC. Used for "Continue working"|

### Notes

|Column|Type|Required|Default|Notes|
|-|-|-|-|-|
|Id|uniqueidentifier|yes|`NEWSEQUENTIALID()`|primary key|
|ProjectId|uniqueidentifier|yes|none|foreign key to Projects|
|Title|nvarchar(100)|yes|none||
|Body|nvarchar(4000)|yes|`''`|the note text|
|CreatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC|
|UpdatedAt|datetime2(3)|yes|`SYSUTCDATETIME()`|UTC. Used to sort notes|

### Why these types

|Choice|Reason|
|-|-|
|`NVARCHAR`, not `VARCHAR`|Unicode, so names in any language (Malayalam, Hindi, emoji) are stored correctly. It costs double the space, and it is what EF Core uses for strings.|
|`DATETIME2`, not `DATETIME`|A larger date range, a chosen precision, and better accuracy. `DATETIME` rounds to about 3 ms.|
|Precision `(3)`|Milliseconds. Whole seconds would make two items created in the same second tie when sorted.|
|UTC|One clock for every user. A server in the EU and users in India agree, and daylight saving cannot create duplicate or missing hours. Convert to local time only when displaying.|
|`BIT` for `IsPinned`|A true or false flag.|
|`UNIQUEIDENTIFIER` for ids|A GUID, matching the string ids the React app already uses.|
|Empty string with a default, not `NULL`|The React code treats these fields as strings. `NULL` would add a second form of "empty" and a check in every place.|

### Where the limits are enforced

The same limits must exist in three places, so the database is the last line of defence and not the first:

1. The React forms (`maxLength`).
2. The API validation (it returns a clear message).
3. The database column length.

To do: add `maxLength` to the item details field and the note fields in the React forms, to match this table.

## 4\. Relationships

|Parent|Child|Meaning|Foreign key|On delete|
|-|-|-|-|-|
|Users (one)|Projects (many)|a user has zero or more projects, and a project belongs to exactly one user|`Projects.UserId`|cascade|
|Projects (one)|Items (many)|a project has zero or more items, and an item belongs to exactly one project|`Items.ProjectId`|cascade|
|Projects (one)|Notes (many)|a project has zero or more notes, and a note belongs to exactly one project|`Notes.ProjectId`|cascade|

"Exactly one" on the child side comes from `NOT NULL` on the foreign key. Each pair is **one** relationship, described from its two sides. There are no many-to-many relationships.

### Delete behaviour

* **Hard delete everywhere, with cascade. No soft delete.**

  * Deleting a project removes its items and notes in one statement.
  * Deleting a user would remove their projects, and through them their items and notes.
* There is no delete-account feature, so a user is never deleted by the app today. The cascade still earns its place: it prevents orphaned rows and makes "delete project" a single statement.
* A soft-delete flag is for apps that must recover, audit, or keep history. This app has none of those needs. If a delete-account feature is added later, hard delete with cascade, after a confirmation, is what privacy rules usually expect.
* Protection against accidents is in the app (confirmation dialogs) and in backups.

### Decision: no `UserId` on Items and Notes

||Without `UserId` on Items and Notes (chosen)|With `UserId`|
|-|-|-|
|Ownership check|through the project|direct|
|Design|each fact stored once|`UserId` stored twice|
|Risk|none|an item could carry a different user than its project|
|Cascade|one cascade path|a second path from Users to Items, which SQL Server rejects unless set to no action|

Revisit in Task 9 only if measurements show a problem.

## 5\. Keys

|Table|Primary key|Foreign keys|
|-|-|-|
|Users|`Id`|none|
|Projects|`Id`|`UserId` references Users|
|Items|`Id`|`ProjectId` references Projects|
|Notes|`Id`|`ProjectId` references Projects|

Every primary key is a single-column GUID, and every primary key is the table's clustered index.

### Decision: how the GUIDs are generated

The aim is a key that is **not random**, because random GUIDs as a clustered key cause index fragmentation.

|Option|Verdict|
|-|-|
|EF Core's default sequential generator for SQL Server|**Chosen.** No code to write, and it matches SQL Server's ordering.|
|`DEFAULT NEWSEQUENTIALID()` in the script|**Kept**, for rows inserted directly in SQL. It can only be used as a column default.|
|`Guid.CreateVersion7()` in the application|**Not used.** SQL Server sorts GUIDs in an unusual byte order, so a version 7 GUID, which is time-ordered by the standard, is not sequential for a SQL Server index.|
|Cluster on an `IDENTITY` column, keep the GUID as a nonclustered primary key|Valid, but more complex. Not needed here.|

The application does not assign ids. EF Core creates them when a row is added. The script's default is a convenience for manual testing. In Task 9, the fragmentation can be measured with `sys.dm\_db\_index\_physical\_stats`.

### A foreign key column's type

A foreign key column has the **same data type** as the key it references (`uniqueidentifier`). The type is not what makes it a key: the `PRIMARY KEY` and `FOREIGN KEY` constraints do.

## 6\. Normalization

Normalization organizes tables so that one fact has one proper home: no unnecessary repetition, no unrelated data in the same table, and no inconsistencies when data changes.

|Form|Rule|How this design meets it|
|-|-|-|
|1NF|each column holds one value per row|items and notes are rows in their own tables, not lists inside a project row|
|2NF|every non-key column depends on the whole key|every table has a single-column primary key, so partial dependencies cannot occur|
|3NF|a non-key column does not depend on another non-key column|user details live only in Users, and projects reach them through `UserId`. Nothing about the user or the project is repeated in the child tables|

### Per-table check

|Table|Result|
|-|-|
|Users|passes. All columns describe the user|
|Projects|passes. All columns describe the project, and the owner is a foreign key|
|Items|passes. All columns describe the item, and the project is a foreign key|
|Notes|passes. All columns describe the note, and the project is a foreign key|

### Deliberate choices

* **Derived data is not stored.** Progress, counts, and the focus order are calculated from the rows, so they cannot go stale.
* **`UserId` is not copied onto Items and Notes** (see Step 4).
* **Category, Type, and Status are stored as text** in the row, protected by `CHECK` constraints. This is a deliberate small repetition of a short value.

### Decision: CHECK constraints or lookup tables

|Column|Allowed values|
|-|-|
|Projects.Category|Web App, Mobile App, AI / Chatbot, API / Backend, Learning, Other|
|Items.Type|idea, bug, research, refactor, feature|
|Items.Status|captured, backlog, in-progress, done|

|`CHECK` constraint|Lookup table|
|-|-|
|a small, fixed list|values may change often|
|no extra table, no join|values need labels, colours, or sort order stored in the database|
|adding a value needs a schema change (a migration)|adding a value is an `INSERT`|
|simple validation|useful when several tables share the values, or when admins manage them|

**Chosen: `CHECK`.** The lists are small and fixed, the labels and colours already live in the React app, and lookup tables would add tables and joins for no benefit now. If users should be able to create their own categories later, a lookup table or a user-defined category design becomes the better fit.

Consequences to remember:

* The category list now exists in two places (the `CHECK` constraint and the React `categories.js`), so they must stay in sync.
* SQL Server's default collation is case-insensitive, so `Done` would pass the status `CHECK`. The API normalizes these values to lowercase before saving.

## 7\. Constraints

### Naming convention

|Prefix|Meaning|
|-|-|
|`PK\_`|primary key|
|`FK\_`|foreign key|
|`DF\_`|default|
|`CK\_`|check|
|`UX\_`|unique index|
|`IX\_`|ordinary index|

Every constraint that SQL Server allows to be named is named. Reasons: SQL Server would otherwise invent names that differ in each database (so a script that drops one fails when moved from Docker to the host), error messages become readable, and the API can recognize a specific constraint name to return a friendly message. `NOT NULL` cannot be named.

### Constraint list

|Table|Constraint|Type|Rule|
|-|-|-|-|
|Users|`PK\_Users`|primary key|`Id`, clustered|
|Users|`DF\_Users\_Id`|default|`NEWSEQUENTIALID()`|
|Users|`DF\_Users\_CreatedAt`|default|`SYSUTCDATETIME()`|
|Users|`UX\_Users\_Email`|unique index|one account per email|
|Projects|`PK\_Projects`|primary key|`Id`, clustered|
|Projects|`FK\_Projects\_Users`|foreign key|`UserId` references Users, on delete cascade|
|Projects|`CK\_Projects\_Category`|check|one of the six categories|
|Projects|`DF\_Projects\_Id`, `\_Description`, `\_IsPinned`, `\_CreatedAt`, `\_UpdatedAt`|defaults|new id, `''`, `0`, current UTC time|
|Items|`PK\_Items`|primary key|`Id`, clustered|
|Items|`FK\_Items\_Projects`|foreign key|`ProjectId` references Projects, on delete cascade|
|Items|`CK\_Items\_Type`|check|one of the five types|
|Items|`CK\_Items\_Status`|check|one of the four statuses|
|Items|`DF\_Items\_Id`, `\_Status`, `\_Details`, `\_CreatedAt`, `\_UpdatedAt`|defaults|new id, `'captured'`, `''`, current UTC time|
|Notes|`PK\_Notes`|primary key|`Id`, clustered|
|Notes|`FK\_Notes\_Projects`|foreign key|`ProjectId` references Projects, on delete cascade|
|Notes|`DF\_Notes\_Id`, `\_Body`, `\_CreatedAt`, `\_UpdatedAt`|defaults|new id, `''`, current UTC time|
|All tables|`NOT NULL`|not null|on every column|

### Notes

* **Uniqueness is per column.** `Id` is already unique because it is the primary key. A unique rule on `Id` and `Email` together would allow two users with the same email, because the pair would still differ. The rule is a unique index on `Email` alone.
* **Unique index, not both.** A unique constraint and a unique index on `Email` would create two identical indexes. One unique index is used, and it is what EF Core generates.
* A `DEFAULT` is itself a constraint in SQL Server, and it can be named.
* Constraints written beside a column are column-level, and rules involving other tables or conditions are written at the bottom of the table.
* Not added: checks that reject whitespace-only text. The API validates this.

## 8\. Indexes

An index is chosen from a query: what it filters by, and how it sorts. A composite index only helps queries that use its columns **starting from the first one**.

|Index|Serves|Reason|
|-|-|-|
|`Users`: unique on `Email` (`UX\_Users\_Email`)|R1, R2, W1|enforces one account per email, and makes login fast|
|`Projects`: `(UserId, IsPinned DESC, UpdatedAt DESC)` (`IX\_Projects\_User\_Pinned\_Updated`)|R4, R8, R13|filter by user first, then rows are already in focus order, so `TOP 3` reads three entries|
|`Items`: on `ProjectId` (`IX\_Items\_ProjectId`)|R5, R6, R7, R9, R10, W6|foreign key, listing a project's items, and the cascade delete|
|`Notes`: on `ProjectId` (`IX\_Notes\_ProjectId`)|R11, W6|foreign key, listing a project's notes, and the cascade delete|

The primary key on each `Id` already has a clustered index.

### Points to remember

* A column with only two values (like `IsPinned`) is a poor index on its own, because it splits the table into two huge groups. It is the second column of a composite index, after `UserId`.
* SQL Server does not create an index on a foreign key automatically, so the `ProjectId` indexes are added by hand.
* No `INCLUDE` columns on the email index. A covering index would avoid a key lookup, but login runs once per session, so the benefit is negligible and the hash would be stored twice.
* Indexes cost something: every insert, update, and delete also updates each index, and each index uses space. They are added where a query would otherwise read many rows.

### Deliberately not indexed

|Query|Why no index|
|-|-|
|`LIKE '%text%'` searches on name, title, details, and body|a leading wildcard cannot use an index. Each search runs over one user's projects or one project's items, which is a handful of rows. Full-text search is the answer at a larger scale|
|Category filter|`UserId` already narrows to one user's few projects|

### Proving the indexes work

With a few rows, SQL Server scans tables whatever indexes exist, because scanning a tiny table is cheaper. In Task 9, generate about 10,000 rows, use `SET STATISTICS IO ON`, and compare the actual execution plan before and after each index (scan versus seek, and the number of pages read).

### Create the tables

```sql
CREATE TABLE dbo.Users (
    Id            UNIQUEIDENTIFIER NOT NULL CONSTRAINT DF\_Users\_Id DEFAULT NEWSEQUENTIALID(),

CREATE UNIQUE INDEX UX\_Users\_Email ON dbo.Users (Email);

CREATE TABLE dbo.Projects (
    Id           UNIQUEIDENTIFIER NOT NULL CONSTRAINT DF\_Projects\_Id DEFAULT NEWSEQUENTIALID(),
    UserId       UNIQUEIDENTIFIER NOT NULL,
    Name         NVARCHAR(60)  NOT NULL,
    Description  NVARCHAR(200) NOT NULL CONSTRAINT DF\_Projects\_Description DEFAULT '',
    Category     NVARCHAR(30)  NOT NULL,
    IsPinned     BIT           NOT NULL CONSTRAINT DF\_Projects\_IsPinned DEFAULT 0,
    CreatedAt    DATETIME2(3)  NOT NULL CONSTRAINT DF\_Projects\_CreatedAt DEFAULT SYSUTCDATETIME(),
    UpdatedAt    DATETIME2(3)  NOT NULL CONSTRAINT DF\_Projects\_UpdatedAt DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK\_Projects PRIMARY KEY CLUSTERED (Id),
    CONSTRAINT FK\_Projects\_Users FOREIGN KEY (UserId) REFERENCES dbo.Users (Id) ON DELETE CASCADE,
    CONSTRAINT CK\_Projects\_Category CHECK (Category IN
        ('Web App','Mobile App','AI / Chatbot','API / Backend','Learning','Other'))
);
CREATE INDEX IX\_Projects\_User\_Pinned\_Updated ON dbo.Projects (UserId, IsPinned DESC, UpdatedAt DESC);

CREATE TABLE dbo.Items (
    Id         UNIQUEIDENTIFIER NOT NULL CONSTRAINT DF\_Items\_Id DEFAULT NEWSEQUENTIALID(),
    ProjectId  UNIQUEIDENTIFIER NOT NULL,
    Title      NVARCHAR(100)  NOT NULL,
    Type       NVARCHAR(20)   NOT NULL,
    Status     NVARCHAR(20)   NOT NULL CONSTRAINT DF\_Items\_Status DEFAULT 'captured',
    Details    NVARCHAR(1000) NOT NULL CONSTRAINT DF\_Items\_Details DEFAULT '',
    CreatedAt  DATETIME2(3)   NOT NULL CONSTRAINT DF\_Items\_CreatedAt DEFAULT SYSUTCDATETIME(),
    UpdatedAt  DATETIME2(3)   NOT NULL CONSTRAINT DF\_Items\_UpdatedAt DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK\_Items PRIMARY KEY CLUSTERED (Id),
    CONSTRAINT FK\_Items\_Projects FOREIGN KEY (ProjectId) REFERENCES dbo.Projects (Id) ON DELETE CASCADE,
    CONSTRAINT CK\_Items\_Type CHECK (Type IN ('idea','bug','research','refactor','feature')),
    CONSTRAINT CK\_Items\_Status CHECK (Status IN ('captured','backlog','in-progress','done'))
);
CREATE INDEX IX\_Items\_ProjectId ON dbo.Items (ProjectId);

CREATE TABLE dbo.Notes (
    Id         UNIQUEIDENTIFIER NOT NULL CONSTRAINT DF\_Notes\_Id DEFAULT NEWSEQUENTIALID(),
    ProjectId  UNIQUEIDENTIFIER NOT NULL,
    Title      NVARCHAR(100)  NOT NULL,
    Body       NVARCHAR(4000) NOT NULL CONSTRAINT DF\_Notes\_Body DEFAULT '',
    CreatedAt  DATETIME2(3)   NOT NULL CONSTRAINT DF\_Notes\_CreatedAt DEFAULT SYSUTCDATETIME(),
    UpdatedAt  DATETIME2(3)   NOT NULL CONSTRAINT DF\_Notes\_UpdatedAt DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK\_Notes PRIMARY KEY CLUSTERED (Id),
    CONSTRAINT FK\_Notes\_Projects FOREIGN KEY (ProjectId) REFERENCES dbo.Projects (Id) ON DELETE CASCADE
);
CREATE INDEX IX\_Notes\_ProjectId ON dbo.Notes (ProjectId);
```
